## 一、方案结论

“湖岸稿件”应当被设计为一款面向作者、研究者和出版准备人群的**本地优先稿件检查与修订桌面应用**，而不是一个只负责给出抽象评分的“书稿体检工具”。

它的核心价值是：

1. 按论文、纸质出版物、电子书三类目标格式检查稿件；
2. 清楚说明发现了什么问题、依据什么标准、问题出现在哪里；
3. 对低风险、可机械判断的问题提供逐项订正；
4. 让用户在 APP 内确认修改并导出独立修订版；
5. 输出可阅读、可保存、可交给编辑或出版社继续使用的检查报告；
6. 在结果页和报告末尾提供克制、相关、可追踪来源的“湖岸橡树出版评估”入口；
7. 将湖岸橡树已经积累的出版规范、检查流程和后台能力转化为可持续更新的规则与知识库。

第一版不追求功能数量，而追求一个完整、可信、可重复的闭环：

> 导入稿件 → 选择出版目标 → 本地检查 → 查看问题和依据 → 逐项订正 → 复检 → 导出修订稿和报告 → 用户自主选择是否进入出版评估。

该产品既是实用工具，也是湖岸橡树未来出版业务的获客入口、标准内容入口和服务筛选入口。但产品本身必须先有独立使用价值，不能做成强制留资、以广告为主或依赖网站才能运行的营销壳。

## 二、已经确认的产品方向

本方案依据此前讨论，固定以下决策：

### 2.1 本地安装、本地运行

- 采用 Windows 与 macOS 桌面应用形态；
- 稿件检查、机械订正、报告生成和主要导出功能在本地完成；
- 默认不上传稿件，不要求用户先注册；
- 网站用户系统尚未完成时，APP 仍能独立开发、测试和使用；
- 后续通过适配层接入登录、授权、设备管理、出版评估提交和规则更新。

### 2.2 结果页采用“软转化”而非强制营销

- 结果页显示“湖岸橡树出版评估”入口；
- 报告末尾可以显示同一入口；
- 不把广告、水印或跟踪信息写进用户稿件；
- 不以必须注册、必须上传或必须咨询作为查看报告和导出文件的前提；
- 用户点击后才打开网站；提交评估摘要前再次明确确认。

### 2.3 标准条目可追溯

- 每条检查结果必须关联标准名称、标准条目或湖岸解释页；
- APP 内提供简明解释，网站提供更完整的资源页面；
- 官方标准、湖岸解释、工具规则必须分层呈现，不能把湖岸建议伪装成国家标准或行业强制要求；
- 标准内容必须有来源、版本、适用范围和更新时间。

### 2.4 复用湖岸橡树出版体系后台能力

- 复用现有出版体系中的流程、风格指南、检查清单、自动化工具和规则经验；
- 不把 APP 直接绑定到内部目录结构或内部工作流；
- 通过标准化规则包、检查配置和 Provider 接口复用能力；
- APP 产生的用户文件与出版社内部生产项目保持隔离。

### 2.5 产品保持科学、易用、效果明确

- 不用一个看似精确但难以解释的总分替代实际问题；
- 优先给出问题数量、严重程度、是否可自动修复和下一步行动；
- 界面采用渐进式呈现，默认只展示用户当前需要的信息；
- 第一版不加入聊天机器人、云端协作、复杂排版编辑器等会稀释主流程的功能。

### 2.6 湖岸账号入口与可选同步（v1.1 新增）

- 湖岸账号与网站账号为同一账号体系，APP 不建立独立账号；
- APP 界面保留注册、登录入口（欢迎页与设置页），入口常驻但永不强制；
- 未登录（访客）状态下，检查、订正、导出等全部核心功能完整可用；
- 已登录用户可以选择将检查记录同步到网站用户后台；同步必须经用户明确确认，默认不同步；
- 网站用户系统尚在开发中，第一版通过 AuthProvider / SyncProvider 占位实现，入口显示「即将开放」，不发送任何数据；后续对接不改变本地核心。

## 三、产品定位与市场角色

### 3.1 一句话定位

一款在本地检查稿件、解释出版问题、辅助机械订正并导出出版准备文件的桌面应用。

### 3.2 它解决的核心问题

作者通常不知道：

- 稿件是否具备基本的投稿或出版准备条件；
- 论文结构、标题层级、注释和参考文献是否一致；
- Word 稿件中是否存在影响编辑和排版的隐藏格式问题；
- 电子书是否存在导航、元数据、语言、图片替代文本等结构问题；
- 哪些问题可以自己修改，哪些必须交给编辑、排版或出版机构；
- 修改后应当输出什么版本，如何证明原稿没有被覆盖。

“湖岸稿件”不替用户决定作品价值，也不承诺出版结果。它把出版前的技术性、规范性和结构性问题变成可理解、可执行的任务。

### 3.3 目标用户优先级

#### 第一优先级

- 准备投稿或出版中文论文的研究者、教师、研究生；
- 准备自费出版或寻找出版社的中文作者；
- 已完成初稿、需要整理 Word 稿件的文学与非虚构作者；
- 需要从 Word 稿件生成基础 EPUB 的作者和小型内容团队。

#### 第二优先级

- 自由编辑、校对人员；
- 小型出版社和学术机构编辑部；
- 写作课程、研究方法课程和作者社群；
- 需要批量预检投稿稿件的期刊或协会。

#### 暂不优先

- 需要专业 InDesign 排版的成熟出版社生产团队；
- 需要多人实时协作、审稿流程管理的机构；
- 需要 AI 代写、全文润色或内容重写的用户。

### 3.4 在湖岸橡树业务体系中的位置

APP 位于“免费或低门槛工具 → 标准内容 → 出版评估 → 编辑与出版服务”的最前端：

```text
自然搜索 / 社群 / 内容文章 / 作者推荐
                ↓
          下载湖岸稿件 APP
                ↓
    本地检查、订正、导出实际成果
                ↓
       阅读标准解释与资源页面
                ↓
 用户主动选择湖岸橡树出版评估
                ↓
 编辑评估 / 出版服务 / 长期作者关系
```

产品增长应建立在工具可信度上，而不是以强制注册换取一次性线索。

## 四、产品名称建议

### 4.1 推荐名称

- 中文：**湖岸稿件**
- 英文：**Oak Manuscript**
- 副标题：**稿件检查、修订与出版准备**

该名称简洁，既能与湖岸橡树品牌关联，也不会把产品限定为“书稿”“论文”或“电子书”中的单一类型。

### 4.2 对外描述不要使用的名称

- 不建议只叫“书稿健康体检”：容易使论文和电子书用户误以为不适用，也容易让用户期待医学式总分；
- 不建议叫“出版路径导航”：应用范围过窄，不能体现实际修改与导出能力；
- 不建议叫“出版价格测算”：容易把工具降格为获客计算器；
- 不建议使用过度技术化的名称，如“出版预检引擎”。

### 4.3 发布前验证

正式发布前应完成域名、商标、应用商店重名和搜索结果检查。若名称存在法律或市场冲突，可保留 Oak Manuscript 作为产品代号，再选择更通用的正式名称。

## 五、核心使用流程

### 5.1 首次使用

1. 用户看到简短隐私说明：稿件默认只在本机处理；
2. 用户选择“检查自己的稿件”或“使用匿名样本体验”；
3. APP 解释支持格式、不会覆盖原稿以及自动修改范围；
4. 用户选择稿件文件和本地项目保存位置；
5. APP 创建项目并复制只读原稿。

匿名样本体验非常重要。它可以让用户在不交出真实稿件的情况下理解产品价值，也减少首次使用焦虑。

### 5.2 创建检查项目

用户需要选择：

- 稿件类型：论文、纸质出版物、电子书；
- 目标引用格式：默认（推荐，由 APP 自动选定）、GB/T 7714—2025、APA 7、Chicago 18 注释—书目、Chicago 18 作者—日期、暂不检查引用格式；
- 语言：自动识别、中文为主、英文为主、中英混合；
- 检查深度：快速检查、完整检查；
- 是否生成基础 EPUB 预览。

第一版应提供推荐默认值，避免让普通作者理解大量出版术语后才能开始。

「默认」引用体例的自动选择规则（v1.1 新增）：

- 用户不了解或不希望自行选择体例时，保持「默认」即可开始检查；
- APP 按稿件类型与语言的公开映射表选定体例（映射表见 6.2），选择过程确定、可解释，不依赖 AI 判断；
- 检查开始前明确显示「本次将按 ×× 体例检查」，用户可随时改为手动选择；
- 实际采用的体例及「由默认规则选定」这一事实写入项目文件和检查报告，避免用户误以为检查结果适用于其他体例。

### 5.3 检查结果

结果页按以下顺序呈现：

1. 文件和检查目标摘要；
2. 必须先处理的问题；
3. 建议处理的问题；
4. 可自动机械修复的问题；
5. 需要人工判断的问题；
6. 外部工具尚未验证的项目；
7. 标准与参考资源；
8. 导出与出版评估入口。

不推荐使用单一“健康分”。如确需给用户快速概览，可使用状态级别：

- 尚未具备提交条件；
- 可在订正后提交；
- 基本具备编辑评估条件。

状态必须由透明条件生成，并明确“仅代表技术与规范准备程度，不评价学术质量、文学价值或出版可行性”。

### 5.4 订正与确认

每条问题显示：

- 问题标题；
- 严重程度；
- 出现位置；
- 原文短预览；
- 问题解释；
- 参考标准；
- 推荐修改；
- 是否可自动修复；
- 接受、拒绝、暂不处理按钮。

只有明确、低风险、可重复的机械问题允许自动修复，例如：

- 连续空格和 Tab；
- 明显重复标点；
- 特定样式下不一致的段前段后设置；
- EPUB `mimetype` 存放错误；
- EPUB HTML 语言属性缺失；
- 明确可判断的编号连续性问题。

以下问题不得自动修改：

- 改写句意；
- 增删论证；
- 判断引用是否真实；
- 擅自改变作者、机构、日期和参考文献内容；
- 改变诗歌、文学作品或特殊版式的语义结构；
- 自动补写图片替代文本；
- 自动选择作者希望使用的引文体例。

### 5.5 导出

导出页至少提供：

- 修订稿 DOCX；
- 基础 EPUB；
- JSON 检查报告；
- Markdown 检查报告；
- HTML 检查报告；
- 最多 16 页的 PDF 审阅样张；
- 脱敏出版评估摘要；
- 项目完整性验证结果。

导出前显示：

- 原稿未被修改；
- 已接受、已拒绝、未处理问题数量；
- 外部验证是否运行；
- 输出文件保存位置。

### 5.6 登录与同步（可选，v1.1 新增）

- 欢迎页与设置页提供「注册 / 登录湖岸账号」入口；未登录不影响任何核心流程；
- 已登录用户在检查完成页与导出完成页会看到一次同步询问：是否将本次检查记录同步到湖岸账号；
- 询问选项：仅同步本次、总是同步（可在设置中随时关闭）、暂不同步；
- 同步内容分级，默认只含摘要与统计；稿件文件永远需要单独明确确认（详见 8.5）；
- 网站用户系统未完成前，该入口显示「即将开放」，不发送任何数据。

## 六、第一版功能规格

### 6.1 项目与文件管理

#### 输入格式

- `.docx`
- `.epub`
- `.md`
- `.txt`

#### 明确不支持

- `.doc` 旧格式；
- 含宏的 `.docm`；
- InDesign、Pages 等专有编辑格式；
- 扫描 PDF 直接订正；
- 加密或损坏且无法安全读取的文件。

#### 项目结构

```text
project-root/
├── project.json
├── source/          # 只读原稿副本
├── working/         # 当前工作版本
├── checkpoints/     # 用户确认前的检查点
├── reports/         # 内部分析结果
├── exports/         # 用户导出文件
└── logs/            # 不含正文和隐私的本地技术日志
```

#### 文件安全规则

- 永不原地修改用户原稿；
- 使用 SHA-256 验证原稿不变；
- 最多保留 5 个检查点，超出时按明确策略清理最旧检查点；
- 不把文件名、路径、正文、标题或正文哈希发送到分析服务；
- APP 异常退出后可以重新打开项目继续处理。

### 6.2 检查配置

第一版以 20—40 条高置信度规则的最小规则集起步（清单在阶段 0 冻结），以下检查范围按第十八节的里程碑逐步覆盖，不要求首个里程碑一次实现（v1.1 修订）。

#### 「默认」引用体例映射（v1.1 新增）

用户选择「默认」时，按下表自动选定引用体例。映射表随规则包发布并注明版本，属于确定性规则，不依赖 AI 判断：

| 稿件类型 | 语言 | 自动选定体例 |
|---|---|---|
| 论文 | 中文为主 / 中英混合 | GB/T 7714—2025 |
| 论文 | 英文为主 | APA 7 |
| 纸质出版物 | 任意 | Chicago 18 注释—书目 |
| 电子书 | 任意 | 暂不检查引用格式（用户可显式开启） |

- 语言为「自动识别」时，先完成语言识别再套用映射；识别置信度不足时按中英混合处理；
- 该映射是可讨论的初始默认值，正式发布前应经湖岸编辑确认，并可随规则包版本更新；
- 报告必须记录实际采用的体例与映射版本。

#### 论文格式

- 标题、作者、单位、摘要、关键词、正文、参考文献的基本完整性；
- 标题层级与编号一致性；
- 表格、图片、公式标题与引用关系；
- 脚注、尾注与注释编号；
- 文内引用与参考文献对应关系；
- 参考文献重复、缺项和明显格式不一致；
- 中英文标点、空格和全半角一致性；
- 页边距、段落、行距等基础版式提示；
- 适用引用格式的结构性检查。

APP 不能承诺判断研究质量、查重结果、事实真实性或期刊接收概率。

#### 纸质出版物格式

- 扉页、版权页、目录、前言、正文、附录、参考文献等结构提示；
- 章节标题、编号和目录一致性；
- 注释和参考文献一致性；
- 段落样式、手工空格、空行、分页和分节问题；
- 图片文件、分辨率、题注和来源信息提示；
- 页眉页脚、页码、奇偶页和开章页风险提示；
- 适合进入编辑与排版流程的文件清理建议。

APP 输出的 PDF 只作为审阅样张，不宣称是最终印刷版或印前文件。

#### 电子书格式

- EPUB 容器、`mimetype`、OPF、manifest、spine、nav 完整性；
- 标题、作者、语言、标识符等元数据；
- 阅读顺序和目录导航；
- HTML 标题层级和语言属性；
- 图片引用、缺失资源和替代文本提示；
- 内部链接与锚点；
- CSS 基础兼容性和固定尺寸风险；
- 可访问性基础提醒；
- 外部 EpubCheck、Ace 运行状态。

未实际运行 EpubCheck 或 Ace 时，报告必须显示“未运行”，不得显示“通过”。

### 6.3 问题模型

每条问题至少包含：

```json
{
  "issue_id": "unique-id",
  "rule_id": "DOCX-SPACING-001",
  "profile": "print_book",
  "severity": "error|warning|suggestion",
  "title": "连续空格",
  "explanation": "为什么需要处理",
  "location": {
    "part": "document",
    "paragraph": 23
  },
  "preview": "经过截断和脱敏的短上下文",
  "standard_refs": ["OAK-DOCX-STYLE-001"],
  "auto_fixable": true,
  "fix_id": "FIX-SPACING-001",
  "confidence": "high",
  "status": "open|accepted|rejected|resolved"
}
```

### 6.4 报告系统

报告结构建议：

1. 检查目标与文件类型；
2. 结论摘要；
3. 必须处理的问题；
4. 建议处理的问题；
5. 已自动订正内容；
6. 尚需人工判断内容；
7. 外部验证状态；
8. 使用的规则与标准版本；
9. 隐私与限制声明；
10. 标准资源链接；
11. 湖岸橡树出版评估入口。

报告不得出现：

- 夸张的出版成功承诺；
- 未运行工具的通过声明；
- 对稿件学术或文学价值的自动评分；
- 强迫式营销文案；
- 嵌入稿件正文的广告、水印或追踪参数。

### 6.5 标准资源中心

APP 内提供“订正参考标准”页面，支持：

- 按论文、纸质出版物、电子书筛选；
- 查看标准名称、适用范围、来源、版本和更新时间；
- 查看湖岸橡树的简明解释；
- 打开网站完整资源页；
- 显示当前项目使用的规则包版本；
- 对已过期或待复核规则给出提示。

### 6.6 设置与隐私

- 默认网络关闭；
- 默认分析关闭；
- 查看本地项目保存位置；
- 清除本地日志和缓存；
- 查看规则版本；
- 导出诊断信息，且诊断信息不得包含正文、标题、文件名和路径；
- 单独控制是否检查规则更新；
- 单独控制是否打开网站链接。

账号与同步（v1.1 新增）：

- 账号区：注册、登录、退出登录、查看登录状态（网站用户系统开放前显示「即将开放」）；
- 同步区：同步总开关（默认关闭）、同步范围分级设置、查看已同步内容清单、打开网站后台管理与删除已同步记录；
- 登录与同步是「默认网络关闭」原则下由用户显式开启的例外能力，开启后仅访问湖岸白名单域名；
- 退出登录或关闭同步不影响任何本地项目与文件。

## 八、结果页转化设计

### 8.1 出现位置

“湖岸橡树出版评估”只在以下位置出现：

- 检查完成后的结果页底部；
- 导出完成页；
- HTML、Markdown、PDF 报告末尾；
- 标准资源页的相关服务区。

不应出现在：

- 稿件正文；
- 修订 DOCX 或 EPUB 内容；
- 每条问题旁边；
- 阻止用户导出的弹窗；
- 用户未完成检查时的强制注册页面。

### 8.2 推荐文案

主标题：

> 想进一步判断稿件是否适合出版？

说明：

> 湖岸橡树可在您主动提交后，结合稿件类型、篇幅和本次检查摘要提供出版评估。APP 不会自动上传您的稿件。

按钮：

- 了解湖岸橡树出版评估
- 导出脱敏评估摘要
- 暂不需要

### 8.3 点击与提交逻辑

第一阶段：

- 仅打开网站公开页面；
- URL 可以包含来源参数和用户选择的服务意图；
- 不包含稿件标题、作者、文件名、路径、正文和正文哈希。

第二阶段：

- 网站登录完成后，允许用户主动提交脱敏摘要；
- 提交前显示将发送的全部字段；
- 用户再次确认；
- 正文和本地文件仍不发送；
- 若用户希望提供稿件样本，应进入独立、明确的上传流程和隐私说明。

### 8.4 可发送的脱敏字段

- 稿件类型；
- 语言类型；
- 大致字数区间；
- 问题数量与严重程度统计；
- 选择的出版目标；
- 使用的规则版本；
- 用户选择的咨询意图。

默认禁止发送：

- 姓名和联系方式以外的身份信息；
- 稿件正文、标题、文件名和本地路径；
- 参考文献原文；
- 原稿或修订稿哈希；
- 未经用户确认的任何附件。

### 8.5 已登录用户的检查记录同步（v1.1 新增）

同步机制面向已登录用户，目的是让用户在网站用户后台保存、查看自己的检查记录，并可在此基础上发起出版评估。它与 8.3/8.4 的匿名脱敏摘要是**两条不同的通道**：脱敏摘要面向未登录场景，字段严格受限；账号同步以用户明确授权为前提，允许包含更完整的检查内容。二者的规则不得混用。

#### 触发与询问

- 仅在用户已登录时出现，未登录用户永远不会被询问；
- 出现位置：检查完成页、导出完成页；
- 询问选项：仅同步本次、总是同步（可在设置中随时关闭）、暂不同步；
- 默认不同步；选择不同步不产生任何功能限制。

#### 同步内容分级

| 级别 | 内容 | 确认方式 |
|---|---|---|
| 一级（默认） | 项目名称（可修改）、稿件类型、语言、字数区间、检查时间、规则包版本、体例选择、问题统计（数量 / 严重程度 / 处理状态） | 同步询问中默认勾选 |
| 二级（可选） | 完整检查报告（含问题条目、位置与截断脱敏预览） | 同步询问中单独勾选 |
| 三级（默认关闭） | 稿件文件（原稿或修订稿） | 每次单独明确确认，显示文件名、大小与用途 |

#### 隐私与控制规则

- 首次同步前逐项展示将发送的字段，用户确认后才发送；
- 用户可在网站后台查看、下载和删除已同步记录，删除请求必须在服务端生效；
- 同步失败只提示、不阻塞本地流程，不自动重试上传稿件文件；
- 退出登录、订阅到期或网站故障不影响本地项目、报告和导出文件；
- 同步数据只用于向用户本人提供服务与经其授权的出版评估，不用于训练模型，不向第三方共享；
- 传输使用 HTTPS 且仅限湖岸白名单域名，服务端存储遵循网站隐私政策。

#### 实现方式

- 通过 `SyncProvider` 实现（见 11.4）：第一版为本地占位（仅记录用户同步偏好，不联网），网站用户后台与同步 API 完成后替换为真实实现；
- 同步负载使用带版本号的 JSON schema，`project.json` 记录同步状态（时间、范围、对应检查版本），保证可追溯、可重放。

## 九、知识库与标准内容建设

APP 的长期壁垒不只是代码，而是“标准来源—湖岸解释—可执行规则—订正建议—真实案例”形成的知识链。

### 9.1 五层知识结构

#### 第一层：官方或权威来源

- 国家标准；
- 引用格式官方手册；
- EPUB、W3C、DAISY 等技术规范；
- 出版机构、图书馆或学术组织公开指南。

每条必须记录来源、版本、发布日期、适用范围和链接。

#### 第二层：湖岸橡树编辑解释

把专业标准翻译成作者能够执行的说明：

- 这条规则解决什么问题；
- 什么情况下适用；
- 什么情况下不适用；
- 常见错误是什么；
- 作者如何自行修复；
- 哪些情况需要编辑判断。

#### 第三层：机器可执行规则

每条规则具有：

- 稳定 `rule_id`；
- 适用格式与稿件类型；
- 输入条件；
- 判断逻辑；
- 严重程度；
- 置信度；
- 自动修复白名单；
- 关联标准；
- 版本和测试样本。

#### 第四层：匿名案例

- 错误示例；
- 修改前后示例；
- 边界情况；
- 不应自动修复的反例；
- 中英文混合情况。

#### 第五层：运营与反馈

- 用户经常忽略的问题；
- 误报、漏报和规则争议；
- 出版评估中反复出现的准备问题；
- 网站文章访问和 APP 规则点击情况；
- 规则更新需求。

运营数据只能记录规则与统计，不得沉淀真实稿件内容。

### 9.2 优先建设的知识专题

#### 论文

- 论文结构与标题层级；
- 摘要与关键词；
- 注释、脚注与尾注；
- 文内引用和参考文献对应；
- GB/T 7714—2025；
- APA 7；
- Chicago 18 两种体系；
- 图表、公式和附录；
- 中英文混排。

#### 纸质出版物

- 稿件进入编辑前的 Word 清理；
- 章节与目录；
- 版权页信息准备；
- 图片、表格与授权；
- 注释和索引；
- 页眉页脚与分页；
- 文学、学术、诗集和公共版权典籍的差异。

#### 电子书

- EPUB 文件结构；
- 元数据；
- 目录与导航；
- HTML 标题和语义；
- 图片和替代文本；
- CSS 兼容性；
- 可访问性；
- EpubCheck 与 Ace 的作用和限制。

### 9.3 版本与治理

- 规则包使用语义化版本；
- 任何规则变更必须有来源、变更原因、样本和回归测试；
- 官方标准更新不应直接覆盖旧规则，应生成新版本并说明兼容性；
- 已发布 APP 能识别规则包版本；
- 规则更新包应签名；
- 高风险或语义性规则必须经过人工编辑审核后才能发布；
- 法律、版权和合同相关内容应注明建议进行专业法律审查。

## 十一、与湖岸橡树出版体系后台的复用方式

### 11.1 可以复用的资产

- 投稿与稿件接收清单；
- 编辑、校对、排版、电子书和 PDF 流程；
- 《文脉》、学术书、文学书、诗集、公共版权典籍等风格指南；
- Word 结构检查、格式清理、脚注检查、参考文献检查；
- PDF 预检和 EPUB 检查工具；
- 报告格式、问题分类和严重程度经验；
- 匿名样本与测试用例。

> （v1.1 待核实：以上清单需对照 oak-publishing-system 仓库逐项核对存在形态与可复用程度，核对结果作为阶段 0 规则来源盘点的输入。）

### 11.2 不应直接复用的内容

- 真实出版项目记录；
- 作者隐私、地址、付款和合同资料；
- 内部员工操作日志；
- 未公开稿件；
- 仅适用于湖岸内部生产的目录路径和权限逻辑；
- 归档目录中的旧版本文件。

### 11.3 推荐的复用架构

```text
湖岸橡树出版体系
  ├─ 风格指南
  ├─ 检查清单
  ├─ 自动化工具
  └─ 人工编辑经验
          ↓ 审核、标准化、匿名化
     规则源与知识源
          ↓ 构建、版本、签名
       APP 规则包
          ↓
    Oak Manuscript 本地核心
```

APP 不直接读取出版体系后台目录，而是使用经过审核、匿名化、版本化的发布包。这样可以：

- 避免内部变更破坏客户端；
- 防止内部隐私进入 APP；
- 保证规则可测试、可回滚；
- 支持不同 APP 版本使用不同规则版本；
- 让同一规则未来也可用于网站自助检查或内部生产系统。

### 11.4 后接 Provider 接口

- `AuthProvider`：访客模式 → 网站账号和 PKCE 登录；第一版 UI 即保留注册 / 登录入口，Provider 返回「即将开放 / 未登录」状态（v1.1 修订）；
- `LicenseProvider`：本地免费模式 → Pro 年费授权和设备管理；
- `EvaluationProvider`：打开公开页面 → 用户确认后发送脱敏摘要；
- `SyncProvider`：本地占位（仅记录同步偏好）→ 用户确认后将分级检查记录同步到网站用户后台（见 8.5，v1.1 新增）；
- `StandardsProvider`：内置规则 → 签名规则包更新；
- `UpdateProvider`：手动下载 → 签名应用更新；
- `FeedbackProvider`：本地记录 → 用户主动发送不含正文的规则反馈。

## 十二、技术架构

### 12.1 推荐技术栈

> （v1.1 决策：确认采用 Electron + Python sidecar 组合，接受安装包体积与双运行时带来的打包、更新成本；第一版开发期间不中途更换技术栈，Tauri 等替代方案仅在基础版稳定后评估。）

- 桌面壳：Electron；
- 界面：HTML、CSS、JavaScript，第一版不必引入重型前端框架；
- 本地检查核心：Python 3.11+；
- Electron 与 Python：受控 CLI/sidecar，以严格 UTF-8 JSON 通信；
- 配置：JSON；
- 规则内容：JSON/YAML 构建为只读 JSON 规则包；
- 报告：JSON、Markdown、HTML；
- PDF 样张：Electron 打印或可靠的本地渲染方案；
- Windows 打包：便携包和后续安装器；
- macOS 打包：`.app`/DMG，后续签名和公证；
- CI：Windows 与 macOS 分平台构建和测试。

### 12.2 运行结构

```text
Renderer（无 Node 权限）
        ↓ IPC 白名单
Electron Main
  ├─ 窗口与文件选择
  ├─ 项目路径策略
  ├─ Python sidecar 调用
  ├─ PDF 样张导出
  ├─ 外部链接白名单
  └─ Provider 适配层
        ↓ shell=false，参数数组
Python Core
  ├─ DOCX / EPUB / Markdown / TXT 读取
  ├─ 规则检查
  ├─ 白名单机械修复
  ├─ 项目与检查点
  ├─ 报告与修订稿导出
  └─ 完整性与安全验证
```

### 12.3 Electron 安全基线

- `contextIsolation: true`；
- `sandbox: true`；
- `nodeIntegration: false`；
- 预加载脚本只暴露必要方法；
- IPC 使用固定通道和输入验证；
- Python 子进程使用 `shell=false`；
- 禁止 renderer 任意打开本地路径或外部 URL；
- 外部链接只允许 HTTPS 和 Oak 白名单域名；
- 使用系统文件选择器和用户明确选择的项目目录；
- CSP 禁止任意远程脚本；
- 不加载远程网页作为主界面。

### 12.4 文件与压缩包安全

- 规范化绝对路径，拒绝 `..` 逃逸；
- DOCX/EPUB 解包前检查成员数量、单文件大小和总解压大小；
- 拒绝 ZIP 路径穿越；
- 对符号链接和异常文件名采取保守策略；
- 临时目录在项目范围内或系统安全临时目录内创建；
- 失败时不删除原稿；
- 导出前验证目标仍在项目目录内；
- 大文件应提前提示，不让应用无响应。

### 12.5 规则引擎原则

- 规则确定性优先；
- 同一输入和规则版本应产生相同结果；
- 自动修复必须幂等；
- 每条规则独立测试；
- 规则和 UI 文案分离；
- 问题结果可序列化；
- 规则可以按稿件类型、语言和引用体例启用；
- 对无法可靠判断的问题降级为人工建议；
- 不将生成式 AI 作为第一版核心依赖。

### 12.6 未来 AI 能力边界

后续若加入 AI，只建议用于：

- 用更自然的语言解释规则；
- 帮助用户理解某条错误；
- 对用户主动选择的短片段提出非自动应用的修改建议；
- 辅助人工编辑生成评估说明。

必须保持：

- 默认不开启；
- 明确说明是否联网；
- 用户选择具体文本；
- 发送前展示内容；
- 不自动写回稿件；
- 不以 AI 判断替代确定性规则和人工出版决策。

## 十三、授权与商业模式

### 13.1 网站未完成前

建议提供无需登录的本地试用或内测模式：

- 可使用匿名样本；
- 可检查有限长度稿件；
- 可查看问题和标准；
- 可导出基础报告；
- 本地文件永远不因授权到期而被锁住；
- 内测人员可使用临时本地授权，不依赖未完成的网站系统。

### 13.2 推荐分层

#### 免费版

- 中文约 5000 字符或英文约 2000 词以内；
- 基础检查和标准解释；
- 有限的机械修复；
- 基础报告；
- 不要求注册。

#### Pro 版

- 更长稿件；
- 完整检查配置；
- 全部白名单机械修复；
- 完整报告和多格式导出；
- 项目历史和更多检查点；
- 规则包更新；
- 最多 3 台设备。

#### 机构版（后续）

- 多编辑账号；
- 自定义规则包；
- 批量预检；
- 机构模板；
- 本地部署或受控工作区。

### 13.3 暂定价格验证

可测试：

- Pro：CAD 149/年；
- 创始用户：CAD 99/年；
- 创始价格限前 100 位或上线后 90 天；
- 机构版单独报价。

上述价格是验证假设，不应在没有用户访谈、付费意愿测试和支持成本数据时视为最终承诺。计价货币与价位还需结合湖岸实际目标市场（境内与北美中文用户的占比）确认后再对外公布（v1.1 修订）。

### 13.4 不建议的变现方式

- 稿件内容广告；
- 出售或训练用户稿件；
- 强制注册后才能查看自己的报告；
- 按单条错误付费解锁；
- 以夸张“出版成功率”诱导咨询；
- 订阅到期后禁止用户打开本地项目或导出已有结果。

## 十四、市场与用户视角的产品调整

### 14.1 从“检测工具”转向“完成任务”

用户不是为了发现 83 个错误而来，而是为了得到一份更适合投稿、编辑或出版的文件。因此首页和结果页都应强调成果：

- 哪些问题已经解决；
- 还有哪些必须由用户决定；
- 可以导出什么；
- 下一步可以做什么。

### 14.2 降低信任门槛

- 首屏明确“默认不上传”；
- 提供匿名样本；
- 明确不覆盖原稿；
- 每条结果可以看到依据；
- 不隐藏误报反馈入口；
- 不把低置信度问题包装为确定错误；
- 在报告中显示规则版本和检查时间。

### 14.3 提高首次成功率

- 使用推荐默认配置；
- 检查开始前自动判断文件是否可安全读取；
- 对常见问题提供一键修复，但默认仍需用户确认；
- 导出后直接提供“打开文件夹”；
- 失败时保留项目和已完成结果；
- APP 内置最小帮助，不要求用户先读长篇手册。

### 14.4 扩大但不稀释适用范围

同一核心可以服务论文、纸质出版物和电子书，但应使用不同检查配置和文案，不能假设所有出版物使用同一版式。文学书、学术书、诗集、公共版权典籍和期刊将来可以增加细分模板，但第一版只做三类主配置。

### 14.5 建立内容获客循环

每条高频错误都可以形成：

```text
APP 发现的问题
      ↓
标准资源页的解释文章
      ↓
搜索与社群带来新用户
      ↓
用户下载 APP 自查
      ↓
匿名规则反馈改进内容与产品
```

这比单独建设大量没有工具入口的文章更容易形成长期积累。

## 十五、尚未充分考虑的机会

### 15.1 “出版准备文件夹”而不只是单个修订稿

未来可把导出扩展为出版准备包：

- 修订稿；
- 检查报告；
- 图片清单；
- 权利与授权待办清单；
- 元数据表；
- 作者确认事项；
- 出版评估摘要。

这会显著提高作者把工具结果交给编辑或出版社时的实际价值。

### 15.2 规则包成为独立资产

同一规则包未来可以用于：

- APP；
- 湖岸橡树内部生产系统；
- 网站轻量自检；
- 期刊投稿预检；
- 机构定制版；
- 编辑培训和课程。

因此规则必须从一开始就拥有稳定 ID、版本、来源、测试和发布流程。

### 15.3 编辑与作者之间的共同语言

报告中的规则 ID、位置和问题状态可以成为作者与编辑沟通的共同语言，减少“请统一格式”这类模糊往返。未来可以允许导出“编辑反馈包”，但仍不需要实时云协作。

### 15.4 公共版权典籍和中文古籍处理

湖岸橡树的公共版权中文典籍业务可以形成独特规则包，例如：

- 繁简体与异体字提示；
- 古籍标点和段落差异；
- 底本、校勘和版本说明；
- 公共版权与新增编辑成果边界；
- EPUB 竖排或特殊字符风险。

该方向有差异化价值，但复杂度较高，应放在基础版稳定之后。

### 15.5 教学与机构合作

APP 可作为论文写作、学术规范和数字出版课程的教学工具。匿名样本、规则解释和修改对比天然适合课程演示。机构版可以提供自定义规范，但不能让机构规则污染公共规则包。

### 15.6 无障碍出版作为差异化能力

中文出版市场中 EPUB 可访问性工具较少。持续建设图片替代文本提示、标题层级、语言标识、导航和 Ace 工作流，可以形成比一般“格式检查”更专业的定位。

### 15.7 本地优先本身是品牌资产

在作者对未公开稿件泄露高度敏感的情况下，“默认本地、不强制上传、原稿不可变”可以成为核心竞争优势，应当被产品、网站和隐私政策一致表达。

## 十六、尚未充分考虑的风险与应对

### 16.1 误报导致用户不信任

**风险：** 出版规范具有语境，机械规则可能把合理写法标成错误。  
**应对：** 使用置信度、适用范围和“人工判断”分组；提供拒绝与反馈；低置信度规则不自动修复；用匿名反例测试。

### 16.2 规则来源与版权

**风险：** 某些标准手册受版权保护，不能复制大段原文。  
**应对：** 保存标准元数据和短引用，主要使用湖岸解释与链接；遵守合理引用；正式发布前进行版权和法律审查。

### 16.3 用户把报告当成出版承诺

**风险：** 用户可能把技术预检结论理解为学术质量或出版可行性评价。  
**应对：** 反复区分技术准备、编辑评估和出版决定；不用“保证”“通过出版社”等文案；出版评估由独立人工流程完成。

### 16.4 本地应用的安全与信誉成本

**风险：** 未签名 Windows/macOS 应用会触发系统警告，影响转化。  
**应对：** 内测阶段明确提示；正式发布前完成代码签名、macOS 公证、校验值、下载页和版本记录。

### 16.5 Electron 体积与性能

**风险：** 安装包较大，超长稿件或大型 EPUB 可能占用大量内存。  
**应对：** 设定安全上限；分阶段解析；显示真实进度；对超限文件给出建议；后续评估 Tauri 等替代方案，但不在基础版中途重写技术栈。

### 16.6 网站尚未完成造成授权阻塞

**风险：** 账号、支付和设备系统延期，APP 无法发布。  
**应对：** 核心不依赖网站；提供本地免费/内测模式；Provider 接口占位；网站后接不改变项目文件格式和检查核心。

### 16.7 订阅限制伤害本地文件控制权

**风险：** 用户担心订阅到期后失去自己的项目。  
**应对：** 永不锁定本地文件；订阅只限制新检查或高级功能；已有项目、报告和导出文件持续可访问。

### 16.8 支持成本被低估

**风险：** Word、EPUB、操作系统和字体差异会产生大量边界问题。  
**应对：** 只支持明确格式；提供诊断包；建立匿名样本库；按文件类型统计失败原因；在正式推广前进行小规模受控内测。

### 16.9 规则更新造成结果漂移

**风险：** 同一稿件在不同时间得到不同结果，用户难以解释。  
**应对：** 报告记录规则版本；项目默认固定规则版本；用户主动升级后重新检查；保留旧报告和变更说明。

### 16.10 生成式 AI 使产品同质化

**风险：** 通用 AI 可以快速给出格式建议。  
**应对：** 重点建设确定性检查、原稿保护、可追溯标准、可执行修复、项目版本和出版工作流，而不是与通用聊天工具竞争泛化写作建议。

### 16.11 过度扩展

**风险：** 同时加入排版、写作、翻译、协作、投稿和出版管理会拖垮第一版。  
**应对：** 使用明确的“不做清单”；任何新功能必须证明能提高主闭环完成率或出版业务转化质量。

### 16.12 账号与同步功能稀释“本地优先”信任（v1.1 新增）

**风险：** 引入登录入口和同步机制后，用户可能怀疑“默认本地、不上传”的承诺，社群也可能将其解读为变相收集稿件。  
**应对：** 登录与同步永远可选且默认关闭；同步采用分级明确授权，稿件文件级同步每次单独确认；界面与文案严格区分“本地检查”（默认）与“账号同步”（可选）；隐私政策与 APP 内说明一致表述；网站后台提供已同步数据的查看与删除。

## 十八、开发阶段与执行任务

### 阶段 0：产品与规则基线

目标：建立可开发、可测试、可追溯的基础。

任务：

- 固定产品名称、支持格式、用户流程和不做清单；
- 建立独立项目目录；
- 定义项目文件格式；
- 定义问题模型、规则模型和标准模型；
- 盘点 oak-publishing-system 中可复用的检查工具与清单（只读），冻结第一版 20—40 条最小规则集清单（v1.1 新增）；
- 建立匿名 DOCX、EPUB、Markdown、TXT 样本；
- 定义本地隐私和源稿保护要求；
- 定义网站 Provider 接口；
- 建立基础测试与验收文档。

完成标准：开发引擎无需重新解释产品范围即可开始实现。

### 阶段 1：本地核心 MVP

目标：命令行核心完成完整闭环。

按三个里程碑推进，避免三类配置并行导致无法收敛（v1.1 修订）：

- **M1**：DOCX 输入 + 论文配置 + GB/T 7714—2025（含「默认」体例映射），完成创建、检查、修复、复检、导出全闭环；
- **M2**：纸质出版物配置 + APA 7 / Chicago 18 两种体系 + Markdown、TXT 输入；

任务：

## 二十二、指标与验证方法

第一阶段不要采集正文级行为数据。优先通过用户访谈、主动反馈和不含稿件信息的本地/可选统计验证。

### 22.1 产品价值指标

- 创建项目成功率；
- 完成首次检查的比例；
- 检查后完成至少一项订正的比例；
- 成功导出修订稿或报告的比例；
- 用户认为“发现了原本不知道的问题”的比例；
- 用户愿意在下一份稿件继续使用的比例。

### 22.2 质量指标

- 崩溃率；
- 解析失败率；
- 导出失败率；
- 高置信度规则误报率；
- 自动修复撤销率；
- 原稿哈希异常次数，目标必须为 0；
- 隐私或越权写入事件，目标必须为 0。

### 22.3 业务指标

- APP 下载到完成检查的转化率；
- 结果页到标准资源页点击率；
- 结果页到出版评估页点击率；
- 出版评估提交率；
- 评估线索中真正具备基本稿件准备条件的比例；
- 评估到编辑或出版服务的转化率；
- 工具带来的客户获取成本与传统渠道比较。

### 22.4 指标红线

- 不为提高转化强迫上传稿件；
- 不以稿件正文训练模型；
- 不把文件路径、标题或作者身份作为默认分析字段；
- 不用黑暗模式诱导用户咨询或订阅。

## 二十六、最终判断

“湖岸稿件”值得继续开发，但必须坚持以下判断：

- 它首先是一款能让用户得到修订稿和可执行报告的工具，其次才是获客渠道；
- 它的核心壁垒是可追溯的出版知识、确定性规则、原稿保护和真实工作流，而不是一个模糊的 AI 分数；
- 本地优先能够解决作者最敏感的隐私问题，也允许网站系统稍后对接；
- 结果页的出版评估入口合理，但必须克制、透明、由用户主动触发；
- 账号与同步能力应当增强而不是削弱“本地优先”：登录永不强制，同步永远由用户明确授权、默认关闭；
- 内部出版体系的能力可以复用，但必须经过标准化、匿名化、版本化和接口化；
- 第一版应把 DOCX 与 EPUB 的检查—订正—导出闭环做扎实，不应被价格测算、路径导航、云协作或 AI 写作带偏；
- 真正的产品验证不是检查出多少问题，而是用户是否成功得到更可用的稿件，并愿意继续使用或主动寻求专业出版服务。

按本方案推进，可以在不依赖网站注册系统的情况下先完成独立 APP，再逐步接入湖岸橡树的内容、授权、出版评估和后台生产体系。

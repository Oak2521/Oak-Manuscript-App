## 二、产品结论

湖岸稿件不是一次性演示工具，也不是只提供抽象评分的营销页面。1.0.0 必须是可以销售订阅、持续更新和承担用户数据责任的正式产品，并同时提供：

- Windows 可安装版本；
- macOS Intel 与 Apple Silicon 可安装版本；
- 可嵌入湖岸橡树官网的 Web 版本；
- 湖岸橡树官网统一账号；
- Free 与 Pro 订阅权益；
- 本地确定性检查、批量机械修复、撤销、复检与导出；
- 用户明确同意后的检查结果与元数据同步；
- 可签名、可回滚、可追溯的标准与规则更新。
- 不替代确定性检查核心的可选 AI 建议层，允许用户关闭 AI、使用湖岸 AI，或接入自己的 AI。

桌面端继续坚持本地优先。Web 端采用服务端统一处理，但上传只用于当前任务，默认零留存；任何云端长期保存仅限用户明确确认的结果和元数据，不保存稿件内容。

## 四、冻结的产品原则

### 4.1 源稿与本地文件

- 桌面端永不原地修改用户原稿；
- 原稿在项目创建时生成 SHA-256，任何检查、修复、撤销、导出后必须仍一致；
- 修订结果只写入 `working/`、`checkpoints/` 或 `exports/`；
- 订阅到期、账号退出、网站故障或服务停运不得锁住用户已有本地项目和导出文件；
- 默认不联网、不上传、不记录正文级遥测。

### 4.2 检查与修复

- 确定性规则是产品核心，同一输入与同一规则版本应得到同一结果；
- 仅白名单内的低风险机械问题可自动修复；
- 不自动改写语义、论证、事实、作者信息、参考文献内容或文学表达；
- 自动修复必须幂等、可预览、可撤销、可复检；
- 未真实运行 EpubCheck 或 Ace 时必须显示 `not_run`，不得声称通过。

### 4.3 账号与网络

- 湖岸账号就是 APP 账号，不建立第二套身份系统；
- 欢迎页、全局账号区、设置页和适当的结果/导出位置保留注册与登录入口；
- 桌面端未登录也能完成基础本地闭环；
- 登录本身不等于同意同步；
- 每一种发送行为必须有独立、可撤回的授权。

### 4.4 三端一致与差异

- 三端共享产品模型、规则版本、报告 schema、账号、订阅权益和结果同步协议；
- Windows/macOS 的稿件处理默认在本机；
- Web 在湖岸服务端执行同一核心，但上传文件默认只在任务生命周期内存在，处理后删除；
- 平台能力不同必须明确说明，不以“跨端一致”为理由降低隐私或安全标准。

### 4.5 AI 模式与稿件控制

- AI 是可选建议层，不是确定性检查、机械修复或出版判断的依赖；关闭 AI 时完整本地闭环仍可使用；
- 三种模式固定为“无 AI”“湖岸 AI”“我的 AI”，不得在失败后静默切换模式；
- AI 输出只能形成可审阅建议，不能直接写回稿件、加入批量机械修复或绕过用户确认；
- “我的 AI”凭据不得同步到湖岸账号或结果记录；桌面端只可使用操作系统安全存储，Web 端只允许当前会话内保存；
- 任何实际模型请求都属于独立联网动作，必须由用户主动触发并在请求前说明发送对象与数据范围。

## 五、核心用户流程

### 5.1 桌面端

1. 用户选择访客使用或登录湖岸账号；
2. 选择本地稿件与项目目录；
3. 选择论文、纸质出版物、电子书或综合检查；
4. 引用体例保持“默认”或手动选择；
5. 本地检查并查看问题、依据和位置；
6. 打开“批量自动修复”预览，集中查看全部拟修复内容；
7. 一次确认后原子执行整批修复；
8. 必要时撤销到修复前检查点；
9. 复检并导出修订稿与报告；
10. 已登录用户看到同步询问，先查看字段，再选择仅本次同步、以后询问或不同步。

### 5.2 Web 端

1. 用户登录湖岸账号或在允许的 Free 匿名范围内开始；
2. 明确同意本次稿件发送到湖岸处理服务；
3. 上传文件进入隔离、限时、零留存任务；
4. 服务端运行与桌面端同版本的检查核心；
5. 用户查看问题、批量修复预览和结果；
6. 生成的修订稿和报告在短期下载窗口内提供；
7. 任务结束或超时后删除稿件、工作副本、片段和导出临时文件；
8. 只有用户明确选择时，才长期保存结果与元数据到账号后台。

## 六、批量自动修复：P0 交互与安全契约

“批量”必须真实表示一次预览、一次确认、一次事务，而不是让用户逐项点选。

### 6.1 计划阶段

- `plan-fixes` 只读分析当前项目，不修改 working 文件、问题状态或检查点；
- 返回全部可修复候选，至少包含：问题 ID、规则 ID、标题、位置、修改前预览、修改后预览；
- 生成 `plan_id`，绑定当前 working 文件哈希、问题集合、规则包名称/版本/哈希及候选集合；
- UI 在一个可滚动窗口完整列出所有拟修复项；
- 用户可以不逐项阅读，直接在列表总览后一次确认；
- 取消或关闭预览不产生任何写入。

### 6.2 执行阶段

- 执行必须携带有效 `plan_id`；
- working 文件、问题集、规则包或候选集合变化后，旧计划失效，要求重新预览；
- 修复前建立检查点；
- 整批执行必须原子化，任何失败均恢复修复前状态；
- 只修复计划中列出的候选，不得顺便处理其他 `open` 或 `accepted` 问题；
- 成功后记录 applied 数、检查点 ID、规则版本与审计摘要；
- 再次执行同一批计划必须被拒绝或得到零变更，不得重复损坏文件。

### 6.3 撤销

- UI 提供“撤销上一次批量修复”；
- 提供检查点列表，显示时间、原因、涉及项数和可恢复状态；
- 恢复前先保存当前状态为安全检查点，使撤销本身也可撤销；
- 缺失、损坏或越界检查点不得改变 working 文件；
- 恢复后重新分析，并保持源稿哈希不变。

## 七、引用体例

引用体例选项顺序：

1. 默认（由 APP 后台按检查类型自动选择）；
2. GB/T 7714—2025；
3. APA 7；
4. Chicago 18 注释—书目；
5. Chicago 18 作者—日期；
6. 暂不检查引用格式。

“默认”使用确定性解析器，输入包括检查类型、主要语言和引用结构信号。APP 必须显示最终体例、理由、置信度和解析器版本，并允许用户覆盖后重新检查。低置信度时降级为引用结构与一致性检查，不强行套用体例。

## 八、湖岸统一账号、订阅和设备

### 8.1 身份

- 目标身份平台：网站现有 Supabase 认证体系；
- 桌面端通过系统浏览器 PKCE 登录，不在 APP 内嵌远程密码页；
- Web 使用同一 Supabase 会话；
- 令牌进入操作系统安全凭据存储或安全 HTTP-only Web 会话，不进入项目文件、日志和同步负载；
- 支持注册、登录、退出、密码恢复、会话过期和设备撤销。

### 8.2 订阅

正式版采用 Free + Pro：

| 能力 | Free | Pro |
|---|---|---|
| 匿名样本体验 | 完整 | 完整 |
| 本地项目访问与已有导出 | 永久可用 | 永久可用 |
| 新稿检查长度/次数 | 有明确额度 | 更高或不设常规稿件限制 |
| 规则覆盖 | 基础规则 | 完整规则与高级规则包 |
| 批量机械修复 | 有限 | 全部已发布白名单修复 |
| 报告与导出 | 基础 | 完整多格式导出 |
| 项目历史与检查点 | 基础 | 增强 |
| 标准更新 | 安全必要更新 | 完整标准与规则更新 |
| 账号结果同步 | 有限历史 | 完整历史与跨端查看 |
| 设备 | 1 台建议值 | 最多 3 台建议值 |

具体额度和价格在正式公开前通过用户访谈与受控内测验证，不把旧方案中的 CAD 价格当作既定承诺。

### 8.3 授权降级

- 订阅到期不删除、不加密、不锁定本地项目；
- 已完成报告和导出持续可访问；
- 新检查或 Pro 专属能力可降级；
- 网站故障时桌面端按最近一次签名授权宽限运行；
- 授权缓存必须有签名、过期时间和明确错误状态。

## 九、结果与元数据同步

### 9.1 同步范围

普通账号同步只允许结果与元数据，禁止同步：

- 稿件正文、标题、摘要、关键词、短预览；
- 原稿、修订稿或任何片段；
- 文件名、本地路径、用户名或设备目录；
- 参考文献、脚注和图片原文；
- 文件哈希、正文哈希或可反推出稿件的内容指纹。

允许字段采用服务端和客户端双重白名单，例如：

- 随机项目 ID 与 run ID；
- 文件格式、检查配置、语言类别、长度区间；
- 请求与最终引用体例；
- 规则包与 APP 版本；
- 按严重程度、维度和处理状态汇总的数量；
- 仅含规则 ID、严重程度、维度、处理状态、是否可修复的问题记录；
- 外部验证状态、导出状态、创建时间；
- 同步 schema 版本和幂等 ID。

### 9.2 确认流程

- 默认关闭；
- 登录后在检查或导出完成位置非阻断询问；
- 发送前展示全部字段，不使用含糊的“同意同步全部”；
- 选项至少包括“仅同步本次”“以后仍询问”“暂不同步”“不再询问此项目”；
- 用户可以在 APP 与网站后台查看、导出和删除云端记录；
- 删除云端记录不删除本地项目；
- 同步失败不阻塞检查、修复或导出；
- 队列幂等、可取消、可重试，重复提交不能生成重复记录。

## 十、标准、规则与自动升级

### 10.1 当前标准资产审计结论

Claude 0.0.1 当前包含：

- `config/standards.json`：13 条标准来源；
- `config/rule-packs/oak-rules-1.0.0.json`：35 条规则；
- 6 条可自动修复规则。

已发现缺口：

- `OAK-BOOK-PREP-001` 与 `OAK-EPUB-BASICS-001` 仍是概要占位，不是完整公开标准说明；
- GB/T 7714 的官方来源 URL 为空；
- APA 与 Chicago 的引用检查覆盖较浅；
- TXT 没有专属规则；
- 一些 Oak 解释缺少完整来源、适用范围、反例或维护责任人；
- 13 条来源不能被宣传为“完整覆盖全部稿件标准”。

### 10.2 标准注册表要求

每条标准至少具有：

- 稳定 `standard_id`；
- 标题、来源类型、版本、发布日期与适用范围；
- 官方来源或可公开核验的权威入口；
- Oak 解释页 slug；
- 版权使用方式与可引用范围；
- 状态：active、superseded、under_review、deprecated；
- 发布者、审核者、更新时间；
- 关联规则和测试证据。

### 10.3 升级机制

- 内置一份经过审核的标准和规则包，保证离线可用；
- 用户主动开启联网更新后，`StandardsProvider` 获取签名 manifest；
- manifest 包含版本、兼容 APP 范围、SHA-256、签名、发布时间、变更说明与回滚目标；
- 客户端先下载到隔离目录，验证签名、哈希、schema、规则白名单和兼容性后再原子安装；
- 更新失败保留旧版本；
- 新建项目默认使用最新已安装稳定版；
- 已有项目继续固定创建时的规则版本，不在后台悄悄改变结果；
- 用户选择升级已有项目时，先显示规则差异并创建检查点；
- 至少保留一个上一稳定版本以便回滚；
- 紧急撤回通过签名撤回清单处理，不删除用户旧报告。

## 十一、跨平台应用架构

### 11.1 共享层

- Python 确定性核心继续保持标准库优先；
- 规则、标准、报告和同步 schema 平台无关；
- 新 UI 逐步迁移为共享 TypeScript + Vite 前端，以适配 Electron 与 Web；
- 桌面专属能力通过受控 bridge 注入；
- Web 专属能力通过同源 HTTPS API 提供；
- 所有平台使用相同契约测试，防止同一稿件得到不同结果。

### 11.2 Windows

正式交付至少包含：

- x64 NSIS 安装器；
- 可选便携 ZIP；
- 应用图标、文件版本、发布者信息和卸载入口；
- 安装、首次启动、升级、降级保护、卸载和残留数据说明；
- 代码签名与时间戳；
- SHA-256、发布说明和回滚链接。

### 11.3 macOS

正式交付至少包含：

- Apple Silicon arm64 `.app` / DMG；
- Intel x64 `.app` / DMG，或经验证的 universal 构建；
- hardened runtime、签名、公证与 stapling；
- Keychain、文件选择、中文路径、sidecar、导出和自动更新验证；
- Apple Silicon 与 Intel 实机或可信硬件测试证据。

Windows 机器只能验证构建配置，不能声称 macOS 包可运行。没有 Apple 开发者账号、公证凭据和 macOS 执行环境时，正式 macOS 发布门禁保持未通过。

### 11.4 Web

推荐部署：

- 湖岸官网静态前端继续由 Netlify 承载；
- Web APP 路径目标为 `/manuscript/app/`，最终 canonical 与重定向必须在网站仓库核对后确定；
- 长任务检查核心部署到隔离容器服务，推荐 Cloud Run 类受控容器；
- Netlify Functions 或同源 API 负责会话校验、签发短期上传/任务凭证和结果代理；
- 临时对象存储设置短 TTL、服务端删除和生命周期兜底；
- 任务队列、限额、并发、超时、防病毒、ZIP 炸弹和路径穿越防护必须启用；
- Web 结果领取使用短时会话授权的一次性 POST：不签发可重放的持久下载 URL；首个已认证同源请求独占结果，服务端完成临时对象删除和终态墓碑后才返回字节。并发/二次领取失败；清理失败不返回；清理后若传输或本机保存失败，用户重新检查；
- 日志禁止记录请求正文、文件名、对象键中的原始名称或内容哈希。

## 十二、Provider 边界

正式架构至少保留：

- `AuthProvider`：Supabase 登录与会话；
- `LicenseProvider`：Free/Pro、宽限和设备；
- `SyncProvider`：确认后的结果与元数据同步；
- `EvaluationProvider`：独立的出版评估提交流程；
- `StandardsProvider`：签名标准与规则更新；
- `UpdateProvider`：签名 APP 更新；
- `FeedbackProvider`：用户主动发送的脱敏规则反馈。
- `AIProvider`：三种 AI 模式、供应商配置、凭据隔离、请求预览和建议输出边界。

Provider 故障不得进入 Python 检查核心，也不得使已有本地项目不可用。Renderer 不直接持有密钥、令牌或任意网络权限。

### 12.1 AIProvider 冻结契约（2026-07-28 用户确认）

1. 提供“无 AI / 湖岸 AI / 我的 AI”三种显式模式；默认无 AI，不把 AI 设为检查核心的隐含依赖。
2. “我的 AI”支持 OpenAI、Anthropic、Google Gemini 等云 API，自托管 OpenAI-compatible HTTPS 服务，以及本机 Ollama / LM Studio；官方云供应商标签绑定固定官方端点，自定义地址必须选择 OpenAI-compatible；非本机服务只允许 HTTPS，本机 HTTP 仅限精确 loopback 地址。
3. 用户凭据永不进入同步载荷、日志、报告或 Renderer 回读数据。桌面端使用系统级加密存储；Web 端只保留于当前会话，刷新或退出后必须重新提供。
4. AI 只能产生建议和解释，不能静默改稿、替代规则结论、进入白名单机械修复或自动写回 working 文件。
5. “我的 AI”属于 Pro 权益，但调用不消耗湖岸 AI 配额；供应商费用、速率限制和数据政策由用户自己的服务承担。
6. “我的 AI”失败时不得静默回退到湖岸 AI；应显示稳定错误并保持稿件、本地检查与既有配置不变。

首个实现里程碑交付模式、配置和安全持久化；第二个交付可信单条问题上下文、完整发送预览、10 分钟一次性确认和只读建议；第三个交付 30 分钟一次性建议审阅，模型文本不持久化且不改稿；第四个交付供应商无关有界 HTTP 客户端与适配路由。第五个里程碑（alpha.41）只接入 OpenAI-compatible、Ollama、LM Studio 的非流式 Chat Completions：固定 `/chat/completions`、系统/用户双消息、唯一 assistant 文本响应，继续执行 HTTPS/loopback、禁重定向/Cookie/代理、容量/超时/媒体和凭据回显门禁。第六个里程碑（alpha.42）增加不可达、超时、服务拒绝、重定向、响应不兼容、响应超限和凭据回显的安全提示；失败消费旧计划，只能重新生成零请求预览并再次确认，不自动重试或回退；真实 `127.0.0.1` HTTP 夹具证明 socket/请求和连接重置路径。第七个里程碑（alpha.43）以固定 headless LM Studio 组合发现并拒绝服务端静默模型替换，只允许普通文本中的精确空工具数组，并完成成功/替换拒绝/超时/不落盘的窄验收。OpenAI、Anthropic、Gemini 官方云与湖岸 AI 仍未接入；任何单组合验收都不得写成产品级全面支持。

## 十三、安全与隐私门禁

- Electron 保持 `contextIsolation: true`、`sandbox: true`、`nodeIntegration: false`；
- CSP 默认不允许远程脚本，Renderer 网络访问最小化；
- IPC 固定白名单、类型验证、项目路径约束；
- Python 子进程 `shell=false`，只传参数数组；
- DOCX/EPUB/Web 上传均执行成员数量、单文件和总解压上限；
- 拒绝 ZIP 路径穿越、符号链接逃逸和项目目录逃逸；
- 诊断包、日志、崩溃报告和遥测默认不含正文、标题、文件名和本地路径；
- 任何新网络功能必须有零请求的关闭态测试；
- 密钥和签名凭据不进入仓库、安装包日志或 CI 公开输出；
- Web 临时稿件删除应有任务完成删除、超时删除和存储生命周期三重保障。
